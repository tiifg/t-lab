# T-Lab: автоматизация feature engineering для RecSys

Автоматизированный поиск признаков для рекомендательной системы на основе Feature DSL, point-in-time executor и итеративного отбора по приросту качества.

**Проблема.** В продакшн-RecSys признаки считаются вручную: ML-инженер придумывает до сотни фичей, программирует их и тюнит окна. Выбор окна, агрегации и фильтра - эвристика, которая не факт что оптимальна. Цель работы - показать, что этот процесс можно автоматизировать.

Работа предлагает инфраструктуру автоматизации feature engineering: декларативный DSL, point-in-time executor с гарантией отсутствия утечек (проверен 7 тестами) и parametric proposer. В отличие от классического AutoFE, где фичи генерируются «вслепую» и потом проверяются на качество, мой подход ставит безопасность генерации на первое место: любая новая гипотеза - от параметрического перебора, LLM-агента или графового эмбеддинга - проходит через один и тот же executor и не может нарушить хронологию.

Параметрический proposer - первая стратегия в этой инфраструктуре. Она нашла 3 фичи, которых не было в ручном baseline, и улучшила NDCG@10 на +1.09 п.п. и AUC на +0.50 п.п. на отложенной выборке. Это доказывает, что инфраструктура работает: она способна находить полезные признаки автоматически, без участия человека.

При этом я отдаю отчет в том, что parametric search - не финальная точка, а baseline автоматизации. Задание явно перечисляет более амбициозные направления (LLM-агент, пишущий SQL; графовые модели; трансформеры на всю таблицу), и я их вижу. Мое решение - осознанный trade-off: за отведенное время и на доступных ресурсах (Free Colab, без API-ключей для LLM) я построила систему, которая гарантированно работает и воспроизводима, а не систему, которая может дать больший прирост, но с высокой вероятностью не заведется.

**Подход.** Было построено:
1. **Feature DSL** - декларативное описание признака как `(entity, agg, metric, window, filter)`.
2. **Point-in-time executor** - гарантирует, что для кандидата `(user, item, t)` признак считается только по событиям `t - window*DAY ≤ ts < t`. Тесты на утечку прилагаются.
3. **Proposer** - генерирует кандидатов из DSL-пространства (параметрические окрестности сильных baseline-фичей, cross-entity ratios, селективные фильтры).
4. **Evaluator + Selector** - оценивает marginal ΔAUC на отложенной выборке и отбирает фичи через forward selection.

В отличие от «попросить LLM написать SQL», все работает на уровне **проверяемых спецификаций**: каждая фича именована, воспроизводима и не может нарушить point-in-time.

## Результаты

Датасет - Yambda 50m (Yandex Music), подвыборка 400 юзеров, time-based split по неделям. Метрики на **test**.

| metric | baseline (33 manual) | + agent (3 new) | Δ |
|---|---:|---:|---:|
| AUC | 0.7981 | **0.8031** | **+0.0050** |
| Logloss | 0.3121 | **0.3098** | **−0.0023** |
| NDCG@3 | 0.5243 | **0.5403** | **+0.0160** |
| NDCG@10 | 0.5539 | **0.5647** | **+0.0109** |
| Recall@10 | 0.6841 | 0.6863 | +0.0022 |
| MAP@10 | 0.4836 | **0.4961** | **+0.0125** |

**Отобрано 3 фичи** из 38 кандидатов. Прирост NDCG@10 +1.09 п.п. - довольно значимый для RecSys на Yambda.

### Отобранные фичи

| Фича | Описание | Почему сработала |
|---|---|---|
| `ui_personalization_7d` | user_item_listen_7d / user_listen_7d | Локальная доля айтема в активности юзера - прямой сигнал персонализации, в ручном наборе такого ratio не было |
| `ui_mean_played_60d` | mean(played_ratio) для пары user-item за 60 дней | Расширяет baseline-окно 30d - для «залипших» пар (повторное прослушивание) 60 дней даёт более стабильную оценку |
| `user_uniq_items_14d` | nunique(item) за 14 дней | Промежуточное окно 7 <-> 30 - новый сигнал активности, не пересекается с baseline |

### Ablation (forward selection на LGBM, val)

| Step | Feature added | Val AUC | Δ vs base |
|---|---|---:|---:|
| 0 | baseline (33 фичи) | 0.7928 | — |
| 1 | + `ui_personalization_7d` | 0.7981 | **+0.0054** |
| 2 | + `ui_mean_played_60d` | 0.7987 | +0.0006 |
| 3 | + `user_uniq_items_14d` | **0.8002** | **+0.0015** |

Каждая фича добавляет независимый вклад. Остальные 35 кандидатов отвергнуты как избыточные (Δ ≤ 0.0005) - их сигнал уже покрыт существующими.
